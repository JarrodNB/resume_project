DECISIONS ALREADY MADE (details in docs/architecture.md "Decisions")
==========================================================================================
- Everything runs in Docker; only Docker Desktop is installed on the host (Windows).
  The repo lives in a WSL2 Ubuntu distro (~/resume_project), not on C:\ (bind mounts from
  C:\ made every Rails request take 5+ seconds).
- SQS for AI work. ElasticMQ locally (LocalStack now needs an account token, so dropped).
- Rails owns all writes. The AI worker reads Postgres directly with the READ-ONLY role
  ai_reader (job + career library for gap analysis; later pgvector memory search), scoped by
  the task's user_id, and returns everything via the ai_results queue. Its table grants come
  from Rails (lib/ai_reader_access.rb, after db:prepare/db:migrate), not the init SQL.
- Duplicate SQS messages: worker receives 1 message at a time; Rails result handling must be
  idempotent (ignore results for AiTask that is finished? = completed/failed). No FIFO.
- Pydantic AI for all agents (OpenAI models); human-in-the-loop via Pydantic AI DEFERRED
  TOOLS (ask_user tool -> run ends with DeferredToolRequests -> worker publishes
  needs_user_input with serialized message history -> Rails stores it on AiTask -> user
  answers -> new task resumes with DeferredToolResults). Planned for AI-assisted career
  library rewriting; gaps are answered in the comparison view instead (no ask_user).
- Langfuse Cloud free tier for tracing (Agent.instrument_all()); Pydantic Evals for evals,
  one dataset + runner per agent; faithfulness (no invented experience) is the top metric.
- GraphQL subscriptions (graphql-ruby over ActionCable, Solid Cable adapter) for live UI updates.
- Auth: REST endpoints for sign up/in/out (JWT in Authorization header), GraphQL for the rest.
- Data model: "career library" (experiences + highlights, projects, educations, skills) is
  the source of truth; resumes are documents whose sections store a JSON snapshot.
- UUID primary keys. Per-service .env files (services/api/.env, services/ai/.env).
- File history lives in git, not in file headers.

==========================================================================================
GOTCHAS LEARNED
==========================================================================================
- Shells (yours and agents') are bash inside WSL2 Ubuntu.
- If the Gemfile lists gems that aren't installed, the api container crash-loops; install with
  `docker compose run --rm --no-deps api bundle install`, not `exec`.
- Long chained docker commands sometimes report "Aborted" but actually keep running;
  check the result before re-running (generators will refuse duplicate names).
- Rails was scaffolded with --skip-git, so the root .gitignore carries the Rails ignores
  (master.key is ignored; credentials.yml.enc is committed on purpose).
- .gitattributes forces LF so scripts run inside the Linux containers.
- Shoryuken doesn't eager load in dev, so config/initializers/shoryuken.rb eager-loads
  app/workers in configure_server. It also doesn't reload code: after editing a worker or a
  service it calls, `docker compose restart api-results-worker`.
- Dev Rails host authorization blocks `api:3000` (container hostname). Browsers use
  localhost:3000, so it only matters for container-to-container HTTP tests (use the IP).
- Executable bits matter now (WSL2 is a real Linux filesystem): new scripts in
  services/api/bin need `chmod +x` and `git add --chmod=+x`, or the api container fails with
  "Permission denied".
- `uv add` in a `run --rm` container only updates pyproject/uv.lock; rebuild the ai image
  (`docker compose build ai`) before the new package is importable.
- S3Mock runs as uid 1000: don't mount a named volume as its store root (root-owned, every
  request then fails with a generic S3 InternalError).
- Langfuse Cloud (new orgs): legacy read APIs return 410. Read data via
  /api/public/v2/observations and /api/public/v3/scores (basic auth with the project keys).
- pytest disables Langfuse (LANGFUSE_TRACING_ENABLED=false in tests/conftest.py) because the
  ai container loads the real .env.
- Marcel: detect upload types from bytes only; passing `name:` lets a text file named .pdf
  through.
- shadcn CLI init is interactive; it was run with `-t vite -b radix -p nova --no-monorepo -y
  --no-rtl < /dev/null`. Components import `cn` from the official `cn` npm package (correct).
- Radix components need ResizeObserver in jsdom; src/test/setup.ts stubs it.
- The Cursor browser tool sometimes returns stale snapshots/screenshots; confirm with
  Runtime.evaluate (location.pathname, DOM reads) before assuming an app bug.
- The first aiTaskUpdated result takes ~2-4s while the cable connects ("Loading..." shows).
- __pycache__ folders in services/ai are root-owned (written by the container): delete them
  with `docker compose run --rm --no-deps ai rm -rf <dir>`, not from the host.
- The ai worker doesn't reload code; restart it after Python edits.
- LinkedIn: fetch only the single job a user pasted (never crawl). If scraping starts failing
  with "couldn't read this job posting", LinkedIn changed its layout: update the selectors in
  scrapers/linkedin/linkedin_job_html_to_page.py and the fixtures in tests/fixtures/linkedin.

STEP 3 (DONE): QUEUE ROUND TRIP — what exists now
==========================================================================================
User chose: Shoryuken, a separate api-results-worker compose service, subscription included.
  - AiTasks::EnqueueAiTaskService(user:, task_type:, input:, subject:) creates a queued
    AiTask and publishes {ai_task_id, user_id, task_type, input} to ai_tasks (marks the task
    failed if SQS is unreachable).
  - Python: worker/queue_messages.py (Pydantic AiTaskMessage / AiResultMessage),
    task_handlers.handle_ai_task (echo), main.process_task_message (publish result, then the
    task may be deleted; invalid messages are left for the dead-letter queue; handler crashes
    publish a generic "failed" result).
  - AiResultWorker (Shoryuken) -> AiTasks::ApplyAiResultService: ignores finished tasks
    under a row lock, then triggers ApiSchema.subscriptions.trigger(:ai_task_updated, ...).
  - Subscription aiTaskUpdated(id): ownership-checked, returns current state on subscribe.
    WebSocket auth = JWT in `?token=` on /cable (ApplicationCable::Connection, honours the
    denylist). Solid Cable in dev with its own api_development_cable database.
  - Message formats are documented in docs/architecture.md "Queue Messages".

STEP 4a (DONE, commit 94159b4): RESUME PARSING
==========================================================================================
User chose: the ParsedResume schema as proposed; Rails stores uploads in S3 and Python
extracts text; parsed results are reviewed by the user before import.
  - Flow: parseResume(file: Upload!) mutation -> ResumeImports::StartResumeParsingService
    (PDF/DOCX by magic bytes, 5 MB max) -> Active Storage blob in S3 -> AiTask parse_resume
    with input {source_file: {key, filename, content_type}} -> worker downloads, extracts text
    (documents/), runs agents/resume_parsing_agent -> result {parsed_resume: ...} ->
    user edits -> importParsedResume(aiTaskId, parsedResume: JSON) ->
    ImportParsedResumeService (career library records + blank user profile fields: contact
    details, summary; no resume is created; once per task via ai_tasks.accepted_at).
  - Tracing: one Langfuse trace per task (ai_task.<type>, user id, ai_task_id metadata).
  - Evals: evals/datasets/resume_parsing_cases.yaml (5 synthetic cases), deterministic
    evaluators (faithfulness, experience match, section recall, warnings). First run: 1.0 on
    every score (~$0.02). The set is too easy; add harder cases (multi-column PDFs, long
    careers, mixed date formats). Seen live: degree "B.S. Computer Science" duplicated the
    field of study -> good candidate for a new case.
  - Verified: 14 pytest, 49 RSpec, ruff + rubocop clean, and a live end-to-end run
    (PDF upload -> OpenAI -> import -> duplicate import refused).
  - Not done: production Active Storage service is still :local (switch to :amazon at deploy).

STEP 4b (DONE, commit 7dfd6da): LINKEDIN JOB SCRAPING
==========================================================================================
User chose: one job site at a time, deterministic scraping (no "hand the page to an LLM"), the
Job is created automatically when the result arrives, minimal jobs UI. Greenhouse was built
first and then REMOVED at the user's request: companies embed Greenhouse in career pages
that open jobs in pop-ups, so users have no link to paste. Job seekers browse job boards, and
LinkedIn is the one whose job pages load without a login (Indeed/Glassdoor/ZipRecruiter return
401/403 to plain HTTP). Decision + ToS note in docs/architecture.md.
  - Flow: scrapeJob(url) -> Jobs::StartJobScrapingService (LinkedIn links only; reduces
    /jobs/view/<id>, /jobs/view/<slug>-<id>, /comm/jobs/view/<id>, /jobs/...?currentJobId=<id>
    to https://www.linkedin.com/jobs/view/<id>/; rejects jobs already saved) -> AiTask
    scrape_job -> worker GETs linkedin.com/jobs-guest/jobs/api/jobPosting/<id> (no login) ->
    services/ai/scrapers/linkedin reads the top card + description by class name ->
    job_postings/ splits bullets by headings (<br> lines are turned into <p>s first so
    <strong>Heading<br><br></strong> reads as a heading) -> sorting agent ONLY when no
    requirement heading matches (returns bullet numbers, never text) -> {scraped_job: ...} ->
    ApplyAiResultService creates the Job under the row lock (task subject, AiTask.job).
  - Failures shown to the user: unsupported link, 404 (closed posting), page without a job
    title (login wall / new layout). 429, 5xx, and LinkedIn's 999 are retried via SQS.
  - Web: /jobs (list), /jobs/new (paste link), /jobs/new/:aiTaskId (live status, then opens the
    job or shows warnings), /jobs/:id (read-only detail). useAiTaskUpdates moved to
    features/ai-tasks (shared with resume import).
  - Evals: evals/datasets/job_posting_extraction_cases.yaml (8 synthetic cases in LinkedIn's
    markup; 6 heading cases, 2 LLM-fallback cases), all scores 1.0, ~$0.0004/LLM case.
  - Verified: 113 pytest, 144 RSpec, 43 Vitest, ruff/rubocop/tsc/oxlint clean; live run against
    real LinkedIn jobs (GM, Stripe, Affirm, Evlo AI parse correctly; GM saved end to end with 9
    requirements / 4 nice-to-haves and no LLM call; Greenhouse link refused; the same job pasted
    as a search-page link refused as a duplicate).
  - Not done: a live run that hits the LLM fallback on a real LinkedIn job (no heading-less
    posting found yet; the fallback is covered by evals and tests).

STEP 4c (DONE): GAP ANALYSIS
==========================================================================================
User chose: gap analysis is ONLY a comparison of the career library with the job (no
questions to the user; the user will respond to gaps in the same view, next), and the Python worker reads the database
directly with the read-only ai_reader role instead of receiving a snapshot.
  - Flow: analyzeJobGaps(jobId) -> GapAnalysis::StartGapAnalysisService (job must have
    requirements, library not empty, no analysis of this job already queued) -> AiTask
    analyze_gaps (subject = Job, input {job_id}) -> worker reads job + library in one
    REPEATABLE READ read-only transaction (services/ai/database/) -> labeled prompt
    (R1/N1 requirements; SUMMARY, E1, H1, P1, ED1, S1 library entries) -> gap_analysis_agent
    (output validator retries on missing/repeated/unknown labels) -> code copies evidence text
    by label -> {gap_analysis: GapAnalysisResult} stored on the AiTask.
  - Job.latestGapAnalysis returns the newest task; re-running creates a new one. Deleting a
    job nulls its tasks' subject (costs keep counting).
  - Web: "How you match" card on /jobs/:id (features/gap-analysis/): run, live progress (also
    after reload), failure + retry, verdicts (Met / Partly met / Gap) with cited evidence.
  - ai_reader grants: SELECT on jobs + career library tables + users(id, summary) only
    (the REVIEW.txt item is done). No DB reset needed; the rake task revokes the old grants.
  - Evals: evals/datasets/gap_analysis_cases.yaml (7 synthetic cases), deterministic
    evaluators (coverage, evidence validity, verdict accuracy, gap recall, evidence recall);
    all 1.0 after one prompt fix (adjacent tech counts as partial), ~$0.0014/case.
